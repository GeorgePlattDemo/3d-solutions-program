Read README.md, EVIDENCE.md, SUPERVISED-LABORATORY-CELL-TRIAL.md, and the document or implementation directly affected. Identify the requested outcome, its owning file, and the agreed starting revision.

Preserve that argument and the existing terminology. Do not reorganize, soften, broaden, or replace it to fit a preferred style or template.

## Respect ownership and evidence

*Authority category: Current System Behavior*

Program owns research, proposed trials, candidate engineering, findings, and development decisions. System owns the application and shared operational job meaning. Store owns its facts, evaluation, economics, answers, and refusals. Physical implementation and operating permission remain local responsibilities.

Reference another owner’s work rather than recreating competing authority. Shared terms come from [System’s definitions](https://github.com/GeorgePlattDemo/new-system/blob/main/docs/DEFINITIONS.md).

Support consequential claims with identifiable sources or artifacts. Preserve dates, scope, assumptions, and material limits. Distinguish models from operating results, generated commands from physical execution, software tests from commissioning, and candidate engineering from adopted capability.

Program does not restate or change System’s protected Store pin, runtime endpoint, or deployment settings. A Program task does not authorize changes in System or Store.

This repository is public. Preserve source attribution and applicable notices. Do not bulk-publish private customer, business, or contributed material or infer reuse rights from publication.

## Make bounded changes

*Authority category: Current System Behavior*

Complete the task on the smallest appropriate surface. Do not rewrite adjacent material, introduce terminology or dependencies, add fallback behavior, create speculative documents, or expand the research question.

Every new file must contain substantive work with a clear purpose. Prefer improving the existing owner document to creating another layer around it. Preserve distinct evidence, decisions, requirements, and rationale when removing or relocating material.

**`main` is the only permitted working branch.** Do not create additional local or remote branches, including task, review, feature, repair or documentation branches. Do not create a branch-creating worktree, rename a branch to evade the rule, or change these instructions to accommodate a tool. If an authorized change cannot proceed on `main`, stop and report the exact blocker. Preserve the prepared work and wait for the conflicting condition to be resolved. Do not force-push, bypass protection or rewrite a repository as a workaround. A prepared change is not complete until its verified contents are on `main`.

The four substantive files are README.md, EVIDENCE.md, SUPERVISED-LABORATORY-CELL-TRIAL.md, and this file. Add findings, experiments, economics, or sources when actual material requires them. Do not create a file for every stage through which one piece of research passes.

## Keep the work useful

*Authority category: Current System Behavior*

Write directly about the mechanism, evidence, question, and next decision. Keep qualifications where they affect meaning without repeating disclaimers or governance commentary.

Research must identify what remains unknown and what evidence would justify continuing, narrowing, changing, or stopping. Engineering must identify requirements, candidate solutions, assumptions, gaps, and proposed tests. Economics must cover the complete service and realistic alternatives.

A simpler solution or a reason to stop is a useful result. Preserve negative findings.

**NO BLOOD ON WOOD.** Software success, simulated motion, or commercial convenience does not resolve physical safety requirements.

## Verify and finish

*Authority category: Current System Behavior*

Inspect the full diff, confirm the intended file scope, check affected links and sources, and run applicable existing checks. The documentary check is **python3 tools/check_program.py**. Hosted CI runs the same check; it does not prove runtime behavior, physical capability, or commercial performance.

Do not invent a checker, report an unrun test as passed, or treat file creation as completion. Report what changed, what was verified and its result, what remains unresolved, and whether the work is integrated or awaits an identified action.

**Complete the task. Preserve the argument. Respect the owners. Leave unrelated work alone.**

## Documentation authority and completion contract

*Authority category: Adopted engineering requirements*

Read the shared [manufacturing meaning contract](https://github.com/GeorgePlattDemo/new-system/blob/main/docs/DEFINITIONS.md#manufacturing-terminology-source-words-versus-physical-requirements), the affected owner's specification/master and the existing conformance register before changing behavior. Definitions govern common meaning; System master chapter 8 governs definition and handoff obligations; Store specification sections 1, 3 and 15 govern registration, evaluation and evidence; Program owns research and laboratory claims. A project name, a source word, existing code or a green test cannot override those responsibilities.

The adopted definitions and specifications govern required behavior. Executable source, identified configuration and verified outputs establish what a particular revision actually implements. A disagreement is a conformance defect: preserve the requirement, identify the affected owner and evidence, and repair the implementation or obtain an explicit requirement decision. Neither a passing test nor existing code silently overrides the adopted contract. Documentation must distinguish adopted requirements, verified implementation, proposed capability and physical qualification.

The current Project 1 proof is maintained acceptance evidence, regenerated from the operative source and configuration when consequential behavior changes. Original sealed publications retain their source identities and historical results. Consequential changes must reconcile the affected definitions, specifications, masters, Program descriptions, current proof, tests, links and operational identities before completion. Preserve full technical content and distinguish modeled results, simulated commerce, commissioned execution and inspected output.

For each bounded change, identify the requirement, owning executable path, failing behavior or missing evidence, affected readers and acceptance condition. Preserve component and feature identities, exact parameter constraints, unresolved requirements and attributable refusals. Do not infer a convenient feature from vocabulary, weaken an assertion, omit work, create a fallback answer, duplicate an evaluator or introduce a project-specific capability exception. If the contract itself must change, state the substantive reason and its consequences explicitly; obtain any necessary owner decision rather than silently redefining success.

Documentation is maintained engineering authority. Amend affected sections in their existing locations, preserving technical depth, rationale, complete examples and useful cross-references. Update current generated evidence through its generator; retain sealed original bytes. Do not freeze the current proof to preserve old numbers. Link live guidance to its current owner and immutable evidence to its exact revision. Check file and heading destinations whenever editing linked material. For the authorized documentation/conformance work, all three repository-root READMEs are frozen byte-for-byte; preserve their destinations and report a conflict rather than editing them.

Implementation proceeds only after the affected normative documentation and acceptance obligations are coherent. A change is complete when required checks pass for its exact revisions, all affected operative documents and evidence agree, and deployment identity has been verified where deployment is in scope. The System master's single conformance register identifies open cross-repository obligations and the evidence needed to close each one. Local masters describe their owning details rather than maintaining competing status lists.

Apply authorized, verified changes to `main` only. If repository settings require a pull request, another branch or unavailable approval, stop and report that exact conflict; do not create or use an additional working branch, bypass protection, weaken verification, or amend the single-branch rule. Preserve the prepared change and its evidence. A pending commit is not integrated work, and successful source checks do not establish deployment.

Program owns research, proposed trials, candidate engineering, findings, and development decisions. System owns the application and shared operational job meaning. Reference another owner’s work rather than recreating competing authority. Shared terms come from [System’s definitions](https://github.com/GeorgePlattDemo/new-system/blob/main/docs/DEFINITIONS.md). Support consequential claims with identifiable sources or artifacts. Preserve dates, scope, assumptions, and material limits. Distinguish models from operating results, generated commands from physical execution, software tests from commissioning, and candidate engineering from adopted capability.

Program does not restate or change System’s protected Store pin, runtime endpoint, or deployment settings. A Program task does not authorize changes in System or Store.

This repository is public. Preserve source attribution and applicable notices. Do not bulk-publish private customer, business, or contributed material or infer reuse rights from publication.

## Make bounded changes

*Authority category: Current System Behavior*

Complete the task on the smallest appropriate surface. Do not rewrite adjacent material, introduce terminology or dependencies, add fallback behavior, create speculative documents, or expand the research question.

Every new file must contain substantive work with a clear purpose. Prefer improving the existing owner document to creating another layer around it. Preserve distinct evidence, decisions, requirements, and rationale when removing or relocating material.

Use the protected integration and branch hygiene procedure below: one owner-authorized PR branch for this repository, required checks and owner review before any merge. A prepared change is not integrated until its verified contents are on `main`.

The four substantive files are README.md, EVIDENCE.md, SUPERVISED-LABORATORY-CELL-TRIAL.md, and this file. Add findings, experiments, economics, or sources when actual material requires them. Do not create a file for every stage through which one piece of research passes.

## Keep the work useful

*Authority category: Current System Behavior*

Write directly about the mechanism, evidence, question, and next decision. Keep qualifications where they affect meaning without repeating disclaimers or governance commentary.

Research must identify what remains unknown and what evidence would justify continuing, narrowing, changing, or stopping. Engineering must identify requirements, candidate solutions, assumptions, gaps, and proposed tests. Economics must cover the complete service and realistic alternatives.

A simpler solution or a reason to stop is a useful result. Preserve negative findings.

**NO BLOOD ON WOOD.** Software success, simulated motion, or commercial convenience does not resolve physical safety requirements.

*Authority category: Current System Behavior*

**Complete the task. Preserve the argument. Respect the owners. Leave unrelated work alone.**

## Bounded maintenance procedure

*Authority category: Adopted engineering requirements*

1. Identify the requested research/document outcome, exact starting revision and owning file from the map above. For a claim about runtime behavior, identify the actual System or Store source and revision supporting it; a Program edit cannot repair another owner's implementation.
2. Establish the incorrect statement, missing evidence or implementation defect and its acceptance condition before editing. Repair the responsible source within the authorized scope; do not add a band-aid, competing implementation, invented result or undocumented workaround. A blocked source claim remains explicitly unverified.
3. Before removing or replacing material, trace its references, consumers, distinct requirements and historical custody. Name the surviving owner and evidence that nothing required is lost. Keep unresolved or negative findings and do not discard another session's work.
4. For consequential changes, identify the affected owner sources, definitions, specifications, masters, maintained Project 1 proof and tests in the PR. Reconcile those affected within the authorized scope; mark unaffected items with a reason and identify an out-of-scope dependency as unfinished. Regenerate current proof through its existing owner generator; preserve sealed historical bytes and identities.
5. Inspect the full diff and README freeze comparison, run `python3 tools/check_program.py`, and require Program CI for the exact PR revision. Check changed links and attribution. Never weaken, skip or delete a test, invent evidence, omit a requirement or change an expected result merely to obtain success; a genuinely incorrect expectation needs governing source evidence and an explicit explanation.
6. Submit one bounded PR under the protected integration procedure below. Distinguish document verification from System/Store integration and physical validation. Do not claim an engineering repair, commercial result or deployment from a documentary check.

## Protected integration and branch hygiene

*Authority category: Adopted engineering requirements*

1. Start from verified current `main` and record its full SHA. Inspect local changes and concurrent work before editing; preserve work outside the authorized scope. Use exactly one necessary temporary PR branch in each affected repository for the authorized task. Reuse its safe existing task branch; do not create speculative, redundant or parallel branches, branch-creating worktrees or renamed branches to evade this limit.
2. Keep all task changes in one bounded PR per affected repository. Inspect its complete diff, changed-file list and README comparison before publishing. Do not force-push, rewrite history or repositories, bypass protections, weaken required checks, or treat a tool limitation as authority to do so.
3. Run the repository verification commands above and all required PR checks against the exact proposed source and dependency revisions. Record full SHAs and check URLs. A green result from an earlier head is not verification of a later change; reconcile and reverify changed source, dependencies or merge-base consequences.
4. Obtain the owner's review and explicit merge authorization for the exact reviewed change. Permission to implement or open a PR is not permission to merge. Preserve GitHub's required checks and approvals; when the task ends at review, submit the PR and stop. A blocked approval or integration is reported precisely while other independent authorized work continues.
5. After an authorized merge, verify the resulting `main`, checks and content before deleting that task's local and remote branch. For prior merged, abandoned or stray branches, establish their heads, provenance and disposition of every distinct change first; a squash requires content comparison rather than ancestry alone. Delete them only within owner-authorized cleanup after integration or preserved historical custody is established. Retain and report unresolved work instead of discarding it. Report the final branch list and any deletion blocked by access.

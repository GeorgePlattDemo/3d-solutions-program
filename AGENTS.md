# Program Agent Instructions

This repository investigates whether better-defined demand and bounded manufacturing can make useful component work worthwhile at an existing local yard. Improve that instrument without turning it into a larger documentation system.

## Read before changing

*Authority category: Current System Behavior*

Read README.md, EVIDENCE.md, SUPERVISED-LABORATORY-CELL-TRIAL.md, and the document or implementation directly affected. Identify the requested outcome, its owning file, and the agreed starting revision.

The README’s argument is intentional:

**North Carolina’s condition → a possible change in efficient scale → the customer’s project → defined demand → local manufacturing → full-job economics → evidence and participation.**

Preserve that argument and the existing terminology. Do not reorganize, soften, broaden, or replace it to fit a preferred style or template.

## Respect ownership and evidence

*Authority category: Current System Behavior*

Program owns research, proposed trials, candidate engineering, findings, and development decisions. System owns the application and shared operational job meaning. Store owns its facts, evaluation, economics, answers, and refusals. Physical implementation and operating permission remain local responsibilities.

Reference another owner’s work rather than recreating competing authority. Shared terms come from [System’s definitions](https://github.com/GeorgePlattDemo/new-system/blob/main/docs/DEFINITIONS.md).

Support consequential claims with identifiable sources or artifacts. Preserve dates, scope, assumptions, and material limits. Distinguish models from operating results, generated commands from physical execution, software tests from commissioning, and candidate engineering from adopted capability.

Program does not restate or change System’s protected Store pin, runtime endpoint, or deployment settings. A Program task does not authorize changes in System or Store.

This repository is public. Preserve source attribution and applicable notices. Do not bulk-publish private customer, business, or contributed material or infer reuse rights from publication.

## Make bounded changes

*Authority category: Current System Behavior*

Complete the task on the smallest appropriate surface. Do not rewrite adjacent material, introduce terminology or dependencies, add fallback behavior, create speculative documents, or expand the research question.

Every new file must contain substantive work with a clear purpose. Prefer improving the existing owner document to creating another layer around it. Preserve distinct evidence, decisions, requirements, and rationale when removing or relocating material.

Follow the authorized integration path and the active repository protections. Use a bounded review branch and pull request when required to land approved work on protected main. Preserve review and checks; a separate implementation left stranded is not a completed task.

The four substantive files are README.md, EVIDENCE.md, SUPERVISED-LABORATORY-CELL-TRIAL.md, and this file. Add findings, experiments, economics, or sources when actual material requires them. Do not create a file for every stage through which one piece of research passes.

## Keep the work useful

*Authority category: Current System Behavior*

Write directly about the mechanism, evidence, question, and next decision. Keep qualifications where they affect meaning without repeating disclaimers or governance commentary.

Research must identify what remains unknown and what evidence would justify continuing, narrowing, changing, or stopping. Engineering must identify requirements, candidate solutions, assumptions, gaps, and proposed tests. Economics must cover the complete service and realistic alternatives.

A simpler solution or a reason to stop is a useful result. Preserve negative findings.

**NO BLOOD ON WOOD.** Software success, simulated motion, or commercial convenience does not resolve physical safety requirements.

## Verify and finish

*Authority category: Current System Behavior*

Inspect the full diff, confirm the intended file scope, check affected links and sources, and run applicable existing checks. The documentary check is **python3 tools/check_program.py**. Hosted CI runs the same check; it does not prove runtime behavior, physical capability, or commercial performance.

Do not invent a checker, report an unrun test as passed, or treat file creation as completion. Report what changed, what was verified and its result, what remains unresolved, and whether the work is integrated or awaits an identified action.

**Complete the task. Preserve the argument. Respect the owners. Leave unrelated work alone.**

## Shared integration rules

*Authority category: Current System Behavior*

1. One integrated implementation on protected `main`. Required review branches are temporary integration surfaces; never bypass protection or leave a competing implementation behind.
2. Maintain only the implementation paths the current application uses. Store offers only registered operations it handles; its acceptance checks must reject an offered operation without its evaluator. Preserve independently useful evidence and its source identity.
3. One Store commit. System's candidate record, published runtime pin, CI Store checkout and `startup.sh` name the same Store commit, and move together, after System's tests pass against a checkout of exactly that commit.
4. A missing fact stays missing. A Store answer is used only for the definition revision it answers.
5. A change is finished when it is on `main`, CI is green, and every document that describes the changed behavior says the same thing.
